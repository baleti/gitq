#+title: gitq — a typed, categorical query language for git
#+author: baleti

One query language over git's object graph: describe the data you want by
composing small, typed operations, and end the pipeline with what should
happen to the result.

#+begin_example
  gitq 'commits where author alice take 5 /show'
  gitq 'HEAD via parent* where message "fix" /count'
  gitq 'commits pickaxe "some-function" first /worktree'
  gitq 'HEAD via tree.entries.history sort -date first /copy'
#+end_example

A pipeline is =source [step...] [/terminal]=: a source produces typed frames
(=commits=, =branches=, =tags=, =refs=, =worktrees=, =blobs=, =HEAD=, any
ref), steps transform them (=via= morphism paths like
=parent[0].tree.entries[Blob]= compose and type-check segment by segment;
=where= / =sort= / =pick= / =take= / =grep= / =pickaxe= behave as their
SQL/PRQL/jq counterparts), and a =/terminal= acts on the result (=/show=
=/copy= =/count= =/branch-off= =/reword= =/remove= =/worktree= ...).

Everything is validated at parse time against the frame shape actually
flowing through the pipeline — unknown fields, operators that don't fit a
field's type, or morphisms applied to the wrong object are immediate,
specific errors, never silent empty results.  There is no explicit
=contains= keyword: a value right after a field with no recognized
operator between them gets the field type's implicit operator — substring
match for text-shaped fields (=where author bal=, =where date 2026-07=),
equality for numbers (=where parents-count 2=).

The full design — the typed categorical model, grammar, and extension
guide — is in [[file:doc/gitq.org][doc/gitq.org]]; [[file:doc/examples.org][doc/examples.org]] is a set of worked examples
with real captured outputs, including the pickaxe + =diff.lines= workflow
for seeing matched diff content inline.

* History

gitq began as Emacs Lisp inside the [[https://github.com/baleti/git-branch-off][git-branch-off]] package
(=git-branch-off-gitq.el=), where the language, its registries, and its
fail-loud type discipline were designed and battle-tested.  This repository
is the standalone rewrite in Rust: the language is the same, the
completion engine and parser live in one binary, and Emacs and zsh become
thin integrations over it.  (It passed through a Haskell implementation on
the way; the Rust port is verified byte-identical to it across a 145-case
golden corpus — see [[file:tools/corpus.txt][tools/corpus.txt]] — apart from a
short list of deliberate fixes, below.)

* Installation

** Prebuilt binary (no toolchain needed)

Every tagged release ships a Linux x86_64 binary, built and tested by
[[file:.github/workflows/release.yml][the release workflow]]:

#+begin_src sh
  curl -L -o ~/.local/bin/gitq \
    https://github.com/baleti/gitq/releases/latest/download/gitq-x86_64-linux
  chmod +x ~/.local/bin/gitq
#+end_src

The Emacs integration needs no manual step at all: on first use, if no
=gitq= is found on =exec-path=, it downloads the release binary into
the package's own directory automatically — so installing the straight
recipe is the whole setup, and removing the recipe removes the binary
with it.  A user-installed binary on PATH always takes precedence, and
=M-x gitq-install-binary= forces a re-download.

** From source

Requires a Rust toolchain (1.88 or newer — that floor comes from
=ratatui=, used by the scrollback browser).  Note that Debian 13 packages
only 1.85, so =apt install cargo= is not sufficient; use
[[https://rustup.rs][rustup]].  There is no second toolchain
and no optional backend flag: the in-process gix backend is a module, so
one =cargo build= produces the whole thing.

If you installed Rust with rustup and =make= reports =cargo: No such file
or directory=, the toolchain is present but not on your =PATH=: rustup
writes its PATH line to =~/.profile=, which zsh does not read.  Add this to
=~/.zshrc= (the Makefile also looks in =~/.cargo/bin= as a fallback, so the
build works either way):

#+begin_src sh
  . "$HOME/.cargo/env"
#+end_src

#+begin_src sh
  git clone https://github.com/baleti/gitq ~/gitq
  cd ~/gitq
  make install
#+end_src

Installs to =~/.local/bin= (override with =BINDIR=...=).

The completion installers (=install-zsh=, =install-bash=,
=install-zsh-scrollback=) *copy* their files rather than symlinking, so an
installed shell stays working even if the repository is moved or deleted —
but re-run them after pulling a change to =integrations/=.  The Emacs
integration needs nothing: it resolves =gitq= on =exec-path=, so =make
install= is enough.

=make test= runs
the unit suite; =make corpus= runs the golden corpus, which drives the real
binary over a generated fixture repository and checks the CLI surface
end to end — plain output, =--sexp=, the fail-loud error catalogue, and
completion.

** The in-process git backend

Commit-batch resolution and =parent*=/=parent+= closures run in-process
through [[https://github.com/GitoxideLabs/gitoxide][gix]] rather than
through git subprocesses.  The subprocess path is kept as an automatic
fallback on any failure, and =GITQ_NO_NATIVE=1= forces it at runtime, so
one binary can A/B itself — =make corpus= does exactly that, and the two
backends are required to agree byte for byte.

Where it matters: fixed-cost latency on small queries (the live-preview and
per-keystroke completion path), and deep-history walks — gix enumerates
git/git's 81,470-commit closure in 0.08 s when a commit-graph is present
(=git commit-graph write --reachable=; git maintains it automatically on
gc), 20x faster than libgit2 and faster than =git rev-list= itself.

* CLI usage

#+begin_example
  gitq '<pipeline>'             run a pipeline (from anywhere inside a repo)
  gitq --preview '<pipeline>'   run source and steps, never apply a terminal
  gitq --sexp '<pipeline>'      print frames as Emacs Lisp plists
  gitq --complete '<prefix>'    completion candidates for a partial pipeline
  gitq --scrollback            split the current tmux pane's scrollback into
                               command+output entries (add --sexp for Emacs,
                               --tmux-target PANE for another pane)
#+end_example

=--scrollback= is a separate subsystem from the query language — it reads
the terminal, not git, so it needs a tmux session but no repository.  It
splits captured scrollback into one entry per command, best-effort, by
detecting shell prompts (override the prompt pattern with
=GITQ_SCROLLBACK_PROMPT_REGEX=).  Design and the tmux/OSC-133 measurement
behind it are in [[file:doc/scrollback.org][doc/scrollback.org]].

* Emacs integration

[[file:integrations/emacs/gitq.el][integrations/emacs/gitq.el]] provides =M-x gitq= with per-token contextual
completion (candidates and annotations come from the binary, so they can
never drift from the parser), a debounced live preview of results while
typing, and a results buffer: =RET= visits the object at point (via Magit
when available), =b= branches off, =c= copies the SHA.  Re-invoking =gitq=
from a results buffer pre-fills the minibuffer with the query that built it.

#+begin_src emacs-lisp
;; Doom Emacs, packages.el
(package! gitq
  :recipe (:host github :repo "baleti/gitq"
           :files ("integrations/emacs/gitq.el")
           :branch "main"
           :depth full))
#+end_src

The =gitq= binary must be on =exec-path= (or set =gitq-executable=).

[[file:integrations/emacs/gitq-scrollback.el][integrations/emacs/gitq-scrollback.el]] is a separate, independently-loaded
companion for the scrollback subsystem: =M-x gitq-scrollback= captures the
current tmux pane and opens a =gitq-scrollback-mode= buffer whose movement
is *entry-based* — =j=/=k= jump whole command+output groups (like the
standalone =gitq --scrollback-browse= TUI), =h=/=l= (and =TAB=) fold an
entry's output, =y= copies its command.  Output colour is rendered by
Emacs's own =ansi-color=.  Add =("integrations/emacs/gitq-scrollback.el")=
to the recipe =:files= above to load it too; it needs a tmux session but
no zsh integration.

* Zsh completion

Entirely per-user — completions live in any directory on your =$fpath=,
no root or system paths involved:

#+begin_src sh
  cd ~/gitq && make install-zsh
#+end_src

If your shell already has a writable =$HOME= directory on =$fpath=
(oh-my-zsh, zinit, antidote, and friends all add one), the link goes
there and *no zshrc changes are needed* — just refresh the completion
cache (=rm -f ~/.zcompdump && exec zsh=).  Stock zsh has no per-user
fpath directory, so in that case the link goes to the XDG data dir
(=~/.local/share/zsh/completions= — completion functions are data,
mirroring the system =site-functions= convention, no new dotfile
directory in =$HOME=) and the installer prints the two required
=~/.zshrc= lines:

#+begin_src sh
  fpath=(~/.local/share/zsh/completions $fpath)
  autoload -Uz compinit && compinit
#+end_src

Override the destination with =make install-zsh ZSH_COMP_DIR=...= —
e.g. =$ZDOTDIR/completions= if you keep zsh config under
=~/.config/zsh=.

Completion inside the pipeline argument delegates to =gitq --complete=, so
zsh, Emacs, and the parser always agree on what is valid where.

** Scrollback widgets

[[file:integrations/zsh/gitq-scrollback.zsh][integrations/zsh/gitq-scrollback.zsh]] adds two ZLE widgets over the
scrollback subsystem (both need tmux):

- =\eb= (Meta-b) browses the current pane's scrollback in an interactive
  entry browser, overlaid with =tmux display-popup=.
- =\ee= (Meta-e) sends the scrollback to Emacs (=emacsclient= →
  =gitq-scrollback-open-from-file=).

#+begin_src sh
  cd ~/gitq && make install-zsh-scrollback
#+end_src

Both keys are ordinary =bindkey= bindings you can rebind.  Unlike =_gitq=
these are *sourced*, not autoloaded, so the installer just prints the one
=source= line for =~/.zshrc=.  There are deliberately no OSC-133
shell-integration hooks: tmux consumes those markers, so gitq detects
command boundaries by prompt heuristics instead (tune with
=GITQ_SCROLLBACK_PROMPT_REGEX=) — the reasoning, measured against real
tmux, is in [[file:doc/scrollback.org][doc/scrollback.org]].

* Bash completion

Same delegation model as zsh — no grammar is duplicated.  bash calls
=gitq --complete=; zsh calls =gitq --complete-annotated=, which adds the
registry's own kind and description for each candidate so the menu can
group them without keeping its own copy of the grammar:

#+begin_src sh
  cd ~/gitq && make install-bash
#+end_src

That copies =integrations/bash/gitq.bash= into
=~/.local/share/bash-completion/completions/gitq=.  Most distributions'
=bash-completion= package auto-sources that directory; if yours does not,
the installer prints the one line to add to =~/.bashrc=:

#+begin_src sh
  source ~/.local/share/bash-completion/completions/gitq
#+end_src

Override the destination with =make install-bash BASH_COMP_DIR=...=.
Completion works both with the pipeline quoted (=gitq 'commits wh<TAB>= →
=gitq 'commits where'=) and unquoted (=gitq commits wh<TAB>=); bash lists
plain candidates rather than the categorized menu zsh's =compsys= draws,
which is a display nicety, not required behavior.

* Differences from the Emacs Lisp original

The language is unchanged; a few behaviors are adapted to a real terminal,
each failing loud rather than degrading silently:

- =/copy= uses =wl-copy= / =xclip= / =xsel= / =pbcopy= (errors if none is
  installed) instead of the Emacs kill ring; =/insert= prints the SHA.
- =/branch-off= and =/mark= require their name/label argument (the original
  prompted in the minibuffer); =/amend= and =/commit= without a message
  open =$EDITOR=, as git normally would.
- =/remove= is implemented directly (=git rebase --onto=) with clean-tree
  and is-ancestor guards; =/reword= currently only rewords HEAD.
- =/regex/= patterns and the =regex= operator use the Rust =regex= crate's
  syntax — a near-superset of POSIX ERE, but leftmost-first rather than
  leftmost-longest.  gitq only ever asks match-or-not, never match extent,
  so the difference is not observable in query results.  (The Emacs Lisp
  original used Emacs regexp syntax; the Haskell implementation used POSIX
  ERE.)  =git grep= and pickaxe patterns are ERE in all three.
- =where date after/before= parses dates properly (timezone-aware) instead
  of comparing lexically.

* Fixed in the Rust port

These behaviours differ from the last Haskell release (0.7.0) on purpose.
Each was a silent wrong answer or a documented gap.

- *The tokenizer no longer discards characters it does not recognise.*
  0.7.0 dropped =+ % & ! ? : ; ( ) # $ = @= on the floor, mid-token, so a
  query quietly became a different query: =where author @lice= searched for
  ="lice"= and matched =alice=.  Unusable characters are now an error, and
  the word class was widened so =@{upstream}= and a bare =+= tokenize as
  themselves.
- *=where= with no conditions is an error.*  It used to parse as a
  keep-everything no-op — the only step that did.
- *=where <flag> is true= works.*  =is= compared the flag's boolean against
  the literal string ="true"=, so the natural spelling silently matched
  nothing while the bare =where <flag>= worked.
- *Worktree =modified= / =staged= / =untracked= are populated.*  They were
  declared on the shape and never filled in, so they read as false forever.
- *=path GLOB= after a =where= on a path-carrying shape.*  =path= is both a
  field and a step keyword; the parser used to read =... where content x
  path "*.txt"= as a second condition substring-matching the literal glob.
- *=diff.hunks= covers root commits.*  =diff.lines= passed =--root= and
  =diff.hunks= did not, so a root commit's hunks came back empty.
- *New: the =hunks= morphism*, the standalone factor of =diff.hunks=, so
  =via diff via hunks= composes and =diff.hunks == diff . hunks= holds.
